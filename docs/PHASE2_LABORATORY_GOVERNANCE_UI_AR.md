# المرحلة الثانية — حوكمة المختبر وتحديث الواجهة

## ما تم تنفيذه

- إضافة `evaluateLaboratorySessionGovernance` لتقييم الجلسة دون تعديل بياناتها.
- إظهار بوابة مرئية داخل `LaboratorySessionPanel` تشمل:
  - المعيار والإصدار.
  - الجهاز ولقطة المعايرة.
  - اكتمال البيانات الخام.
  - أثر الحساب والتدقيق.
  - سلسلة حيازة العينة.
  - هوية المراجع.
  - فصل المنشئ عن المراجع.
- منع زر الاعتماد في واجهة الجلسة عندما لا تكون الجلسة جاهزة رسميًا.
- وسم المسار الحالي بوضوح على أنه `diagnostic_only` بدل ترك المستخدم يستنتج أنه اعتماد مختبري.
- إضافة حقول هوية منظمة لمنشئ الجلسة ومراجعها في نموذج البيانات.
- الحفاظ على التوافق مع الجلسات القديمة واختبارات المسار التشخيصي؛ لم يتم حذف `legacyDiagnosticOnly`.

## القرار السلوكي

الجلسة الحالية يمكن إنشاؤها وتشغيل الاختبارات والتقارير التشخيصية، لكنها لا تعرض اعتمادًا رسميًا ما لم تحمل أدلة قابلة للتتبع وهوية مراجع منظمة مختلفة عن هوية المنشئ.

## التحقق

- `npm run lint` — ناجح.
- `npm test` — ناجح: 116 ملف اختبار و671 اختبارًا.
- `npm run build` — ناجح.
- `npm run test:e2e` — ناجح: 18 اختبارًا.

## الخطوة التالية المقترحة

ربط إنشاء الجلسة بمصدر سجل المعايير والأجهزة الفعلي، ثم إضافة نموذج إدخال رسمي للمعيار، رقم الجهاز، لقطة المعايرة، وهوية المستخدم المصادق عليه قبل فتح مسار الاعتماد.

## الحزمة الثانية — ربط السجلات بالجلسات

أصبحت جلسة المختبر تحفظ `standardSnapshot` و`equipmentCalibrationSnapshots` داخل عقد الحوكمة الخاص بها. يمرر التطبيق أجهزة المشروع إلى الواجهة بعد تحويلها إلى `RegisteredEquipment`، وتعرض شاشة إنشاء الطلب معيارًا مسجلًا وأجهزة المشروع المتاحة للاختيار. لا يتم اعتبار اسم المواصفة النصي وحده دليلًا رسميًا؛ يجب أن تأتي اللقطة من السجل وبإصدار وحالة صالحة.

تمت إضافة سجل ابتدائي مضبوط في `src/services/laboratoryStandardRegistry.ts` لأربع اختبارات الركام الأساسية. السجل قابل للاستبدال أو التوسعة بسجل المختبر المعتمد، وتبقى الجلسات التي لا تختار snapshot موثقة في وضع `diagnostic_only`.

التحقق النهائي للحزمة الثانية: `npm run lint` و`npm run build` و`npm test` بنتيجة 671 اختبارًا ناجحًا و`npm run test:e2e` بنتيجة 18 اختبارًا ناجحًا.
